## 1. Princípios
1. O servidor é a única autoridade sobre moedas, inventário, criaturas, loot, progressão, comércio e compras. O cliente só envia intenções. **[OFICIAL, CLAUDE.md 9]**
2. Um único modelo de direitos e salvamento para inventário, loja e loot, evitando três sistemas incompatíveis. **[OFICIAL, SYSTEMS-OVERVIEW]**
3. Todas as concessões são idempotentes, identificadas por um `grantId` único e registradas no perfil.
4. Valores de balanceamento (preços de jogo, chances, limites) ficam em módulos de configuração, não embutidos no código. **[OFICIAL]** Os pesos do ovo são a exceção: são fixos.
5. Falhas (queda do DataStore, reconexão, fechamento do servidor, compra interrompida) são casos de teste obrigatórios. **[OFICIAL, CLAUDE.md 10]**

## 3. Persistência [PROPOSTA]
- **Armazenamento:** `DataStoreService`, uma chave por jogador, `Player_<UserId>`, com `UpdateAsync` para escrita.
- **Bloqueio de sessão:** o perfil registra `JobId` e timestamp; um segundo servidor não carrega perfil ativo, evitando duplicação por servidores simultâneos.
- **Salvamento:** autosave periódico configurável, ao sair, em `BindToClose`, e imediatamente após eventos críticos (compra, troca, conclusão de chefe).
- **Falha de carga:** o jogador não entra em modo jogável com perfil vazio. Mostra tela de erro e permite nova tentativa. Nunca sobrescrever dados existentes por falha de leitura.
- **Cópia de segurança de dados:** guardar versão anterior do perfil (última boa) para recuperação.
- **Versionamento:** campo `schemaVersion` e funções de migração sequenciais.
- **Limite de tamanho:** o valor de um DataStore tem limite de 4 MB; medir o tamanho do perfil e separar blocos grandes (histórico de mercado) em chaves próprias se necessário.

## 4. Esquema do perfil [PROPOSTA]
```
Profile = {
  schemaVersion: number,
  createdAt, lastSaveAt: number,
  session: { jobId, lockedAt },
  currency: { gold: number, ... },            -- tipos [PENDENTE]
  inventory: { slots: { [slotId]: ItemStack }, capacity: number },
  equipment: { [slot]: itemInstanceId },
  items: { [itemInstanceId]: { itemId, rarity, upgradeLevel(0..10), bound, acquiredAt } },
  creatures: { owned: { [creatureInstanceId]: CreatureData }, active: id? },
  progression: { level, xp, stats },
  quests: { [questId]: { state, step } , cluesFound: {1..8} },
  bosses: { [bossId]: { validWins: number, legendaryGuaranteeClaimed: bool } },
  dungeon: { revivesGrantedByQuest: number, hasThirdRevivePass: bool },
  purchases: { receipts: { [receiptId]: grantId }, entitlements: {...}, eggs: {...} },
  grants: { [grantId]: timestamp },           -- janela de deduplicação
  settings: {...}
}
```
Notas:
- Itens com atributos próprios (melhoria +N) são instâncias com ID único. Itens empilháveis (materiais) são `ItemStack`.
- IDs de itens e criaturas vêm das tabelas em `ServerStorage/Config`. O catálogo de criaturas depende da reconciliação com RPG_02 (**[PENDENTE]**, bloqueio 2).
- Melhoria máxima +10 **[OFICIAL]**; limites de atributo e bônus de até 15% no conjunto Lendário **[OFICIAL]**, valores finais ajustáveis.

## 5. Regras que o modelo de dados precisa suportar [OFICIAL]
| Regra | Campo/mecanismo |
|---|---|
| Garantia do item de chefe Lendário até a 5ª vitória válida por jogador/chefe, com participação real | `bosses[bossId].validWins` e `legendaryGuaranteeClaimed`, gravados pelo servidor ao validar participação |
| Até 3 ressurreições totais por jogador por dungeon (padrão 1, +1 por missão, 3ª por passe Robux) | Contador por tentativa no estado da instância (não no perfil) e direitos no perfil (`revivesGrantedByQuest`, `hasThirdRevivePass`). Reconexão à tentativa ativa **não** restaura ressurreições |
| Ninguém revive aliados | Sem operação de ressurreição de terceiros no contrato de remotes |
| Oito pistas para desbloquear conclusão | `quests.cluesFound` com 8 posições, gravadas sem duplicar na reconexão |
| Spoiler da entidade só após vencer organização e entidade | Flag `progression.truthRevealed` definida só pelo servidor ao fim da dungeon final |
| Mercado entre jogadores com taxa de 3% e histórico | Transação atômica entre dois perfis (ver seção 8) |
| Ovo premium: 3 primeiros sem duplicação, chances condicionais, compra bloqueada após o terceiro | `purchases.eggs = { ownedSpecies = {...}, history = {...} }` |
| Compras não aumentam atributos/loot nem criam pay-to-win | Revisão de cada `GrantType` contra lista de efeitos permitidos |

## 6. Concessão idempotente (`GrantService`) [PROPOSTA]
Toda alteração de posse passa por uma função única:
`Grant(player, grantId, operations[])`.
1. Se `grantId` já existe em `profile.grants`, retorna sucesso sem aplicar (idempotência).
2. Valida todas as operações (espaço, limites, pré-requisitos) antes de aplicar qualquer uma.
3. Aplica tudo ou nada em memória.
4. Registra `grantId` e dispara salvamento imediato quando a origem for compra, troca ou chefe.
5. `grants` guarda apenas uma janela limitada, por tempo e contagem, para controlar tamanho.

Fontes de `grantId`: `ReceiptId` (compras), ID da transação (mercado), `bossId + attemptId` (loot de chefe), `questId + step` (missões).

## 7. Contrato cliente–servidor [PROPOSTA]
- Poucos remotes, nomeados por intenção (ex.: `RequestEquip`, `RequestCraft`, `RequestListItem`). Nenhum remote aceita quantidade, preço ou resultado como verdade: o servidor recalcula.
- Validação de tipo e intervalo de todo argumento, limitação de taxa por jogador e rejeição de IDs que o jogador não possui.
- O cliente recebe um espelho somente leitura do estado necessário à interface.
- Nenhum segredo (tabela de drops, sementes) em `ReplicatedStorage`.

## 8. Compras e mercado [PROPOSTA, sujeito a validação Roblox]
- **Compras:** `MarketplaceService.ProcessReceipt` concede via `GrantService` com `ReceiptId` como `grantId`; retorna `PurchaseGranted` somente após o perfil ser salvo com sucesso. Em caso de falha, retorna `NotProcessedYet`. Compras de passes e restauração em novos servidores verificadas por propriedade no perfil.
- **Ovo premium:** o servidor sorteia com os pesos oficiais renormalizados pelas espécies restantes, registra o resultado no mesmo salvamento da concessão e bloqueia nova compra após três. A interface mostra as chances condicionais antes da confirmação. **Antes de ativar, validar as regras vigentes da Roblox para itens aleatórios pagos [PENDENTE, bloqueio 5].**
- **Mercado:** troca de item contra moeda entre dois jogadores exige operação atômica. Proposta: `MemoryStore`/`UpdateAsync` com reserva (escrow) do item na listagem, taxa de 3% aplicada no servidor, e histórico gravado junto. Cenário de comprador ou vendedor offline precisa de desenho próprio e fica para o M4.3.

## 9. Testes de falha obrigatórios (para M1.2 e M1.3)
1. Jogador sai durante o salvamento; servidor fecha (`BindToClose`) com vários jogadores.
2. Dois servidores tentam carregar o mesmo perfil.
3. DataStore indisponível na carga e no salvamento (simular erro).
4. Mesma compra processada duas vezes (reenvio de `ReceiptId`).
5. Reconexão a dungeon ativa: contador de ressurreições inalterado.
6. Spam de remotes e argumentos inválidos.
7. Migração de `schemaVersion` com perfil antigo.
8. Medição do tamanho do perfil com inventário cheio.
Critério: nenhuma duplicação nem perda de item ou moeda em nenhum cenário.
